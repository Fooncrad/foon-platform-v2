# FOON two-way synchronization: foundation and release guard
Status: CONTRACT ONLY — NO ACTIVE SYNC (2026-10-22)
This work is on an isolated branch above Windows PR #205, not in cloud main.
## Target
All eligible business entities must eventually sync both directions, including categories, items, variants, media, translations, pricing, inventory movements, orders, bookings, tables, business settings and permitted customer references. Never sync passwords, card secrets, private customer keys, raw provider tokens or permission grants without separate server-side controls.
## Invariant
Event UUID for replay prevention; tenant/branch/actor scope checked server-side; per-entity optimistic version; cursor-scoped pull snapshots; durable outbox/inbox within business transactions; atomic idempotency ledger; conflict review; media via authenticated content-addressed uploads; local authorization and cloud revocation.
## What is implemented
`lib/platform/bidirectional-sync-contract.mjs` exports pure validation, optimistic conflict and digest/cursor primitives, with targeted unit tests. This is intentionally NOT a writable API endpoint, database journal, broad row replication or a live integration.
## Required before any activation
1. Design and migrate local/cloud change tables and per-device cursor, scoped by tenant, branch and partition. Plan safe initial snapshot and historic data matching.
2. Per-entity adapters & transaction-safe mutation hooks. Ordering/deletes, media upload, inventory movement and irreversible payments need specialized rules.
3. Authenticated push + pull endpoints: device registration, receipt signing, tenant RBAC/plan checks, 401/403/409 controls, no redirects, reject HTML/preview pages and unsafe transport.
4. Version-aware staging integration test including reconnection, races, duplicate replay, branch isolation, device revocation, compensation, offline age limits, read/write entitlement.
5. Hostinger preview redirect issue fixed and verified on staging. Keep operator's sync pause.
6. Source and signed Windows installer separated from Hostinger API updater distribution, backup/rollback policy reviewed.
No database or production change occurs from this branch until these gates are met.

## Pull cursor correctness (new)
The 0157 migration includes `foon_sync_scope_locks`: every journal writer must acquire the same tenant/branch InnoDB row mutex inside its existing transaction *before allocating* the journal auto-increment identifier, and hold it through commit or rollback. Without commit serialization, transaction B can commit id=12 while A's id=11 remains uncommitted; a polling device advances cursor to 12 and silently misses 11. The mutex prevents this within a scope. All future adapters must use `appendScopedChange` and the same transactional connection; direct inserts bypassing the mutex are forbidden.
This is a source-level concurrency contract; it still requires a real two-session MariaDB integration test and does not authorize syncing live data.

## Authorization-to-transaction service (latest)
`lib/platform/bidirectional-sync-service.mjs` gates each push with a server-verified device context and an explicitly provided business-entity adapter, then records an event and applies its authorized business mutation inside the same DB transaction. Failure rolls back both. Stale or duplicate events do not call the adapter. The pull adapter enforces read grants and tenant/branch scope before calling the journal reader. These functions are **not exposed as HTTP endpoints** and do not establish device authentication; callers must build trusted context from a verified enrollment and current DB grants.
**Critical:** do not call the service with user-submitted `verifiedContext`, arbitrary business adapters or full customer/payment secrets. Schema-aware allowlists, real database tests, durable typed adapters and end-to-end provisioning are still missing; live synchronization remains disabled.

## Entity-specific pull authorization
The journal read service now requires both `sync.read` and a per-entity read grant (e.g. `catalog.read`, `orders.read`, `customers.read`); a device with generic sync read may not download staff/customer contents. A filtered pull still advances over unviewable events: a device whose grants expand later requires an authorized initial snapshot/reconciliation, not a promise that skipped historic data will magically reappear. Sensitive payloads must additionally be projected/redacted by typed adapters before any production endpoint is enabled; full event payloads are NOT production-safe.

## Hostinger preview redirect safety (2026-10-22)
A standalone transport helper `lib/platform/bidirectional-sync-transport.mjs` now requires HTTPS, the dedicated `/api/sync/v1/push` or `/api/sync/v1/pull` pathname, bearer authorization, JSON MIME, successful HTTP status and an explicit `ok:true` response. It sets `redirect:"error"`; HTML preview pages, redirects, unauthorized errors and malformed JSON MUST NOT cause outbox ACK. Its endpoint does **not exist yet**, and helper use is not wired to the Windows worker. This is a fail-closed preparatory contract, not a fix for Hostinger routing.
Before enabling any live device: deploy authenticated server endpoints to staging, test actual Hostinger behavior and signed receipts, validate DNS/IP egress, enforce bounded timeouts, and preserve pending events on failures. Operators have paused sync; this remains unchanged.

## Push receipt and pull cursor validation (new)
`lib/platform/bidirectional-sync-wire-contract.mjs` adds pure wire-response checks. A response with `ok:true` is insufficient to ACK a local event: its receipt must match event UUID, tenant, branch, digest, outcome and next version. A matching receipt is marked **unverified** until a trusted signed-receipt verifier confirms it; no ACK is implemented here. Pull batches require monotonically increasing event IDs and exact tenant/branch scope; their cursor is a candidate and may be persisted only after the local typed business adapter transaction commits. This module does not enable HTTP routes, apply data or unlock sync. Run `npm run test:bidirectional-sync` on a clean checkout and then DB/Windows integration before review.

## Pulled-row verification before delivery
`bidirectional-sync-journal.mjs` includes tenant/branch/source-device IDs in the SELECT. `bidirectional-sync-service.mjs` filters entity-level permissions before `prepareSyncPullEvents` validates each returned journal row's scope, JSON payload and event digest (including actor ID). Corrupt or mismatched rows fail the whole request rather than becoming accepted Windows updates. Additional regression fixtures test branch mismatch, actor substitution and payload corruption. Tests are committed but not yet run in a clean Node environment. This is an internal read service only: no HTTP endpoint, no signed receipt and no production activation.

## Zero-row business writes cannot become journal success
`recordAuthorizedChange` now requires the typed `applyBusinessChange` callback to return literal `true` before committing the transaction; undefined, zero affected rows or unconfirmed outcomes trigger rollback. `requireAffectedBusinessWrite` is an opt-in helper that rejects no-op/multi-row writes, but it is not an authorization or SQL allowlisting replacement. Callers must scope every statement to authenticated tenant and branch, validate domain invariants, and invoke the helper only with trusted, fixed SQL. Add MariaDB transaction and concurrency integration tests before enabling live synchronization. Tests are checked into source but have not been executed here.

## Isolated inventory movement adapter
`lib/platform/bidirectional-sync-inventory.mjs` adds an intentionally isolated `foon_sync_inventory_projection` adapter and tests. It performs a tenant/branch/item-scoped locked read and conditional atomic quantity update within the caller transaction, rejects missing stock, negative balances and zero-row writes. Journal event replay is ignored before business application. **This projection is not the actual FOON catalog inventory.** It is not wired to checkout, POS, merchant stock or HTTP, and no migration has been applied to any database. Before deploying, add verified physical item ownership, decimal units/variants, signed device authentication, server-side typed adapters, real MariaDB transaction tests and release gates.

## Transaction-bound isolated inventory entrypoint
`recordAuthorizedInventoryMovement` now composes the verified-device permission gate, journal deduplication, guarded stock projection update and single transaction commit/rollback. The new unit tests cover one authorized stock movement and denial of a cross-branch movement before transaction start. This operates **only** on the independent staging projection, not real business stock, POS, orders or a live HTTP endpoint. Integration tests on MariaDB and Windows, signed device credential checks and typed production catalog adapters are still required before any release.

## Transaction cleanup hardening
`recordAuthorizedChange` now uses a single `finally` cleanup path: successful commit marks the transaction completed; stale or duplicate events and business failures get exactly one rollback; a failed commit also triggers rollback attempt instead of returning a false success. Unit regression cases cover failed commit and single rollback. This is a source-level safety change; it does not establish the database driver's response to network loss during commit. Such a case still requires event-ID reconciliation before retry or ACK.

## Offline pull atomicity tests
Added `scripts/bidirectional-sync-local-receiver.test.mjs` to the sync suite. It covers one atomic batch commit, rejected server-verification flag, wrong-branch events, stale pull cursors, unconfirmed local writes and failed cursor updates. The receiver stores its cursor only inside the same transaction as typed event application. **The `verifiedServer:true` flag is a trusted-caller contract, not a signature verification implementation.** An authenticated verifier and production-specific event adapters must be wired before accepting network data. These tests are committed but have not been executed in this environment.

## Signed pull batches
`applyVerifiedPullBatch` no longer accepts a boolean `verifiedServer` flag. A pinned Ed25519 server public key and base64url signature are required; `verifySignedPullBatch` binds signature to device ID, tenant, branch, after cursor, next cursor and event contents using a domain-separated deterministic message. Tampered batches fail before any transaction. The public key must originate from trusted enrollment/configuration, never from a network response. The cloud signing endpoint and credential provisioning are not yet implemented; live sync stays disabled. Unit tests exercise locally generated Ed25519 signatures but have not been run in this environment.

## Signed cloud push acknowledgments
`lib/platform/bidirectional-sync-push-receipt.mjs` defines an Ed25519 signed acknowledgment bound to device ID, event ID, tenant, branch, content digest, status and persisted version. Cloud code must sign only after its journal and business transaction commit; the private key stays server-side. Windows must verify with its pinned public key and preserve conflicted events for review. Recorded/duplicate can be marked complete only after verification and durable local acknowledgment storage. There is no live push HTTP integration or device enrollment yet; tests have been committed but not executed here.

## Atomic local outbox acknowledgments
A dedicated `foon_sync_pending_events` queue now records journal event UUID, owning device, tenant/branch scope and content digest. `persistVerifiedPushAcknowledgment` checks this queued event under row lock and writes the signed receipt plus the `acknowledged` state in one local transaction; missing events, cross-scope data, conflicting versions and zero-row state updates fail closed. This is NOT the existing order-only `desktop_sync_outbox` from migration 0156, and neither queue is automatically created by the running Windows application yet. Event enqueue integration and real DB transaction tests remain release blockers. The schema changes are committed only, not applied to databases.

## Durable offline event contents (unapplied migration 0157)
The new `foon_sync_pending_events.event_payload` JSON column stores each validated full change envelope, and `queued_at` provides stable pending delivery order. `readPendingSyncEvents` reloads only the enrolled device's tenant/branch events, verifies each row's event ID and SHA-256 digest, and refuses corrupted data before a network push. This fixes a queue design that previously retained only digests and therefore could not retransmit changes after application restart. These changes update the **not-yet-applied** migration 0157, and do not automatically integrate or replace the existing `desktop_sync_outbox` order flow. Do not apply the migration to production until the full integration and database tests pass.

## Opt-in push sender (not live)
`pushNextPendingSyncEvent` loads one scoped pending event from durable JSON, sends it to the HTTPS sync push path without redirects, validates the signed cloud receipt, and atomically records ACK state. Network errors and invalid receipts leave the event pending. The sender deliberately has no scheduler, no authentication provisioning, no automatic retries and no production endpoint wiring. The cloud `/api/sync/v1/push` handler is not implemented and must verify device identity, enforce typed business mutations, and commit before signing an ACK. The existing order-only desktop sync remains separate. The outbox enqueue insert was corrected to include `event_payload`; no migration was executed on either database.

## Server-side device enrollment (staged, not activated)
Migration 0157 now includes `foon_sync_devices` with a SHA-256 credential digest, tenant/branch/actor identifiers, persisted JSON grants, expiry and revoke/disable flags. `authenticateEnrolledSyncDevice` accepts a device-ID-prefixed random 32-byte bearer credential and loads grants from the database; it rejects invalid tokens, missing enrollment and revoked/expired devices. Tokens must be issued, rotated and revoked by an admin-only trusted enrollment flow, which is **not implemented**. The cloud handler requires an injected authenticator and must not be exported as a public route without that enrollment/integration work. Nothing here creates a device credential or changes production data. The SQL migration must be validated in an isolated database before deployment.

## One-time device enrollment and revocation (staged)
The isolated enrollment adapter creates a cryptographically random device bearer credential, stores only its SHA-256 hash, and returns the raw credential once after the DB commit. It restricts grant names and scopes device revocation to tenant and branch. **Security boundary:** `adminScope.authorizedAdmin` is only a trusted server-side assertion supplied after actual administrator session/role verification; this module does not itself authenticate admins. Do not expose this adapter directly to external requests or treat a client-supplied `authorizedAdmin` flag as authorization. Dedicated admin API, credential rotation, request-level rate limiting, safe secret delivery and full DB tests remain outstanding. The revised migration 0157 remains unapplied.

## Enrollment security correction
`enrollSyncDevice` and `revokeSyncDevice` now demand an injected server-only `authorizeAdmin(session)` callback; they no longer trust a direct `adminScope` argument. The callback must perform real session verification, activity/tenant/branch authorization and return `verifiedServerSide:true` only after that verification. Supplying this flag from HTTP JSON, client-controlled data or an untrusted callback remains forbidden. Tests include forged scope rejection and unauthorized revocation. No API route or real session integration is implemented yet.

## Existing FOON administrator session bridge
`lib/platform/bidirectional-sync-admin-session.ts` now resolves the active manager session through the existing session API, requires `owner` or `manager` tenant membership, excludes platform support impersonation, verifies the requested branch is enabled and belongs to the tenant, and enforces the additional-branch PIN unlock. An administrator endpoint must bind the tenant and branch scope to the request and inject a closure such as `authorizeAdmin: (session) => authorizeCurrentSyncDeviceAdmin(session,{tenantId,branchId})` into the isolated enrollment adapter. **No public enrollment endpoint has been enabled.** Requests must use same-origin/CSRF protections, request throttling, audit records, and credential delivery protections before production activation.

## Feature-gated merchant enrollment HTTP route
A new `POST`/`DELETE` route at `/api/restaurant/sync-devices` uses FOON's existing origin checks, current owner/manager session verification, tenant membership, additional-branch PIN gate, and a transaction-bound mysql2 connection. It is **disabled by default** unless `FOON_SYNC_DEVICE_ENROLLMENT_ENABLED=true` is set explicitly. No production activation is authorized; do not enable until migration 0157, automated integration tests, rate limiting, audit logging, credential delivery safeguards, and operational review are complete. The returned device secret must never be printed to logs or forwarded to unrelated clients. This does not enable `/api/sync/v1/push` or `/api/sync/v1/pull`.

## Feature-gated signed cloud pull HTTP route
`GET /api/sync/v1/pull?tenantId=<uuid>&branchId=<uuid>&after=0&limit=100` now calls the existing signed pull service after authenticating a bearer credential against server-stored `foon_sync_devices`. It is **OFF by default**, requiring `FOON_SYNC_PULL_ENABLED=true` and a configured server-only Ed25519 private key (`FOON_SYNC_ED25519_PRIVATE_KEY`). Invalid authentication/scope is rejected, responses are `no-store`, and the DB connection is released. **Do not enable** before database migration 0157, real tests, device enrollment hardening, and rate limiting. This read endpoint is not the push endpoint; it does not activate bidirectional sync. Windows GET transport still needs query-string support before pull integration; production remains disabled.

## Restricted cloud push endpoint (disabled)
`POST /api/sync/v1/push` now accepts a device bearer credential and a bounded JSON `{change}` envelope, but only for `inventory_movement` applied to the **isolated** `foon_sync_inventory_projection`, never merchant stock or live orders. The handler obtains scope/grants from enrolled-device credentials and signs a push receipt after the business transaction commits. It is gated behind `FOON_SYNC_PUSH_ENABLED=true` (off by default) and requires the private Ed25519 signing key and unapplied migration 0157. No automatic worker runs. Browser-origin checks reject foreign origins when present; device bearer calls do not need browser headers. Real transport and MariaDB integration tests, rate controls and merchant-specific typed adapters are still required before any deployment. Do not enable this route in production.

## Windows pull URL contract
`requestScopedSyncPull` constructs the `GET /api/sync/v1/pull` URL with validated tenant, branch, cursor and page limit. The shared HTTPS transport now allows query strings **only** when all four keys exactly match the validated caller-provided pull scope; arbitrary query strings remain forbidden. Tests cover valid parameters, negative cursors and query injection. **The returned response is not trusted merely because it is JSON**: the Windows receiver must verify its Ed25519 signature with the pinned server key and commit events/cursor in one local transaction using the existing local receiver. No polling loop or production endpoint activation has been added. Migration 0157 remains pending.

## Windows one-shot signed pull coordinator
`pullAndApplyNextSyncBatch` reads the persisted local cursor for one enrolled device and its tenant/branch, fetches a scoped HTTPS pull batch, and forwards it to `applyVerifiedPullBatch`. The receiver checks the pinned Ed25519 cloud key, event digests and versions, then applies typed local events and the cursor in one transaction. Invalid signatures and network failures cannot begin a local write. Concurrent pulls for the same scope must be serialized by the device runner; the receiver also compares its cursor before commit and rejects stale attempts. This is **opt-in library code**, not a timer or active Windows worker. It needs actual typed adapters and a MariaDB integration run before activation. No migrations were applied.

## Signed conflicts require review (staged)
Cloud push now returns a signed `conflict` receipt (version 0 placeholder; not a commit acknowledgment) when the optimistic journal rejects a stale change. Windows verifies the Ed25519 signature, device, event ID, tenant, branch and digest, then atomically marks the local outbox event `conflict` instead of deleting or acknowledging it. Already acknowledged events reject a later conflict. `readPendingSyncEvents` selects only `pending`, so conflicting events are withheld from automatic resend pending operator reconciliation. Real operator review UI and MariaDB integration tests are not yet implemented. Routes and migrations remain disabled/unapplied.

## Windows conflict review metadata (not a UI or auto-resolver)
`listScopedSyncConflicts` now reads only the local device's tenant/branch rows in `conflict` state, revalidates stored JSON event integrity and SHA-256 digest, and returns only safe event metadata (type, ID, operation, base version, update time). It intentionally does not expose payload/customer details, delete, acknowledge, or retry any conflicted event. The actual staff-authorized review UI and audited manual resolution remain to be built. The new tests were registered but have not been run against MariaDB. No migration applied.

## Conflict review privacy tightening
Read-only conflict summaries intentionally exclude `entityId`, as identifiers can contain or correlate with sensitive customer/order references in downstream adapters. They now expose only event ID, type, operation, base version, status and review time. Any later detail view must require a separate audited, entity-specific authorization check. Automated tests were updated, but have not been executed against the current branch.

## Bounded Windows push pass
`pushBoundedPendingSyncEvents` provides an **explicit**, bounded single-device push pass (1–100 events, default 20), repeatedly using the existing signed receipt verifier and durable outbox. It stops at the first signed conflict for operator review, preserves pending rows when offline or when receipts cannot be verified, and never runs on a timer. It is not a production worker and is not integrated with real POS/merchant inventory. Tests were added for acknowledgment/idle, conflict, invalid bound and offline errors but are not yet executed against a real MariaDB instance. No migration applied.

## Windows push-pass local concurrency guard
`pushBoundedPendingSyncEvents` now prevents overlapping calls for the same device/tenant/branch **within a single Node process**, releases its guard even after failures, and fails closed if the same event is returned twice in one pass (to avoid infinite retry loops). This is not a cross-process/distributed lock; the Windows runner must additionally enforce single-instance execution across separate processes and persist retries securely. Two regression tests were added but have not yet run with the full repository. No production activation or migrations.

## Cross-process Windows MariaDB advisory lock
`pushWithMariaDbDeviceLock` acquires a non-blocking `GET_LOCK` scoped to device/tenant/branch on a **dedicated** MariaDB pool connection, runs one bounded push pass on that same connection, then calls `RELEASE_LOCK` before returning it to the pool. If the release fails, the connection is destroyed instead of being pooled with an unknown lock state. No new SQL tables are necessary for the advisory lock. This prevents overlapping sender processes that use the same MariaDB server and lock key, but does not coordinate different database servers or protect independently implemented senders that skip this wrapper. Tests are registered but not yet executed against MariaDB. Production remains disabled.

## Advisory lock unknown-state protection
A failed/interrupted `GET_LOCK` request may leave acquisition status unknown even if the MariaDB server acquired the lock. The Windows wrapper now destroys the dedicated connection unless MariaDB explicitly reports lock acquisition or a definite busy response; successful lock acquisition still requires a verified `RELEASE_LOCK` before pooling the connection. Tests now cover uncertain acquisition and failed release. These are mocked regression tests, not proof against a live MariaDB server. No schema change or production activation.

## Opt-in live MariaDB lock integration test

A real two-connection test is available in `scripts/bidirectional-sync-mariadb.integration.test.mjs`. It holds a Windows sender lock on the first MariaDB connection, verifies a second connection receives `SYNC_PUSH_ALREADY_RUNNING`, releases the first lock, and verifies a third attempt succeeds. The outbox read is stubbed **only** to avoid touching application tables; all advisory-lock SQL runs against the real disposable MariaDB instance. No migration is needed for this isolated lock test.

Set `FOON_SYNC_MARIADB_TEST_URL` to a **test-only** MariaDB URL, then execute `npm run test:bidirectional-sync:mariadb`. Without the variable, the test skips. Never supply a production DB URL. This test has been committed but **not executed** from the current environment; it does not establish that the complete push/pull system works. Other application-level transaction tests and Windows integration are still required.

## Opt-in signed pull MariaDB transaction test
`scripts/bidirectional-sync-pull-mariadb.integration.test.mjs` uses a **single test-only MariaDB connection** with transactional `TEMPORARY` tables, not shared application tables. It verifies that failure after the local entity INSERT rolls back both entity and cursor, then a valid Ed25519-signed event commits both and a stale cursor replay is rejected. It uses `FOON_SYNC_MARIADB_TEST_URL` and is included alongside the advisory lock test in `npm run test:bidirectional-sync:mariadb`. **Never provide a production URL.** The suite has been committed but not executed in this session; full app adapters and end-to-end Windows UI are not validated.

## Signed push ACK on MariaDB (opt-in integration)
Added `scripts/bidirectional-sync-push-ack-mariadb.integration.test.mjs` to the `test:bidirectional-sync:mariadb` suite. Using only connection-local TEMPORARY InnoDB tables, it checks that a tampered cloud Ed25519 receipt cannot change the pending event, that a failed queue state update rolls back an already inserted signed-ACK ledger row, that successful ACK and replay are durable/idempotent, and that a signed conflict is retained for manual review without ACK.
