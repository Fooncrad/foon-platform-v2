# Catalog imports and account image library

Apply additive migration `0092_catalog_import_media_accounts.sql` before deploying this version. It creates account overrides and idempotent import batch receipts. Existing images and catalog records are preserved. Follow the production backup and migration procedure; no production migration is performed by the tests.

All activities have independent CSV imports for categories, items/products/services, option groups and option values/add-ons. Activities using the unified catalog also import variant combinations and their stock. Restaurants retain their canonical option model; a combination inventory import is not presented for them. Each importer lives in its matching catalog section. Templates and UTF-8/BOM support are included. The compatibility menu bulk endpoint uses the same importer.

Import categories first, then products, groups, values and combinations. References use exact Arabic names scoped to tenant, category and product. Ambiguous names, existing categories/items/groups/values, duplicate SKU/combinations, invalid prices and missing references fail rather than overwriting data. `options` uses `اللون=أحمر|المقاس=كبير`. Physical measurements and measured-selling units are accepted for unified catalog products.

Each file has at most 500 rows; batches contain at most five rows. Progress counts committed rows, not merely uploaded bytes. A batch is atomic, including its images. Successful earlier batches remain if a later batch fails. Resume reuses its request key and payload hash, avoiding duplicates after an uncertain response. The pending job is stored in this browser for the specific tenant/section. Reopening the section and pressing Resume continues it; choosing a new file starts a separate job. Reimporting a name is rejected, not silently merged.

Images are optional: `image_1` for categories/values and up to `image_4` for products/combinations. URLs must be direct HTTPS image URLs without credentials, nonstandard ports or redirects. The downloader resolves and pins a public IPv4 address, rejects private/reserved destinations and limits time/bytes. PNG, JPEG and WebP are decoded with a pixel limit, rotated and center-cropped to a square 800×800 JPEG (4:4); invalid images fail the batch. A private `/api/account/library/{id}` copied from the same account is also accepted. External fetching is tested separately from image decoding; disposable DB/browser integration uses owned library files and does not rely on an external image host.

Imported store assets appear in the owner's image library without duplicating the stored blob. Library selection can reuse a store image, or explicitly copy a personal image into the authorized business's public asset storage. Personal library URLs stay private. Product, category, option and combination relations point to tenant-scoped saved assets. The media picker supports category/product/variant images and restaurant resource image fields. Store assets cannot be deleted from the library while referenced by catalog/resources; remove the relationship first.

Admin `/admin/media` controls account-type defaults and individual overrides, including customers. Individual overrides can be reset to type defaults. Stored library files and all assets of the owner's businesses count toward the same file/storage quota. Tenant uploads are billed to the owner, not the manager performing the upload; owner account locks serialize concurrent quota checks. Reducing limits never deletes existing images. Existing profile avatar/logo/cover blobs remain separate fixed-size profile fields, not library files. Preexisting externally linked images do not consume local storage until imported/uploaded.

Validation: `npm run test:catalog-import`; built application and disposable loopback-only `foon_migration_test`: `npm run test:catalog-import:integration`. Include checkout/catalog language regression suites after changes to shared menu/image code.
